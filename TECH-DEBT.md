# Technical debt

- ui/services/inventory.py `update_resource` (PUT `/api/inventario/<table>/<uid>/`, sent by the detail modal in ui/templates/ui/inventario.html): renaming a `uid` does not rename the row. `uid` is the primary key of the five inventory models, and the function sets the new value on the loaded instance and calls `obj.save()`, so a free new uid inserts a second row and leaves the old one, and a uid owned by another item overwrites that item with no error; the `IntegrityError` → "già presente" branch never fires. Write through `model_class.objects.filter(uid=original_uid).update(...)` as `patch_resource` does in the same file, and add a rename test and a collision test to ui/tests/test_inventory_api.py.

- ui/views.py `_serialize_log_entry`: `entry.timestamp.strftime("%d/%m/%Y %H:%M")` formats an aware UTC datetime (`USE_TZ = True`, `TIME_ZONE = "Europe/Rome"` in config/settings.py), so every row of Impostazioni → Log is one or two hours behind the wall clock. Format `django.utils.timezone.localtime(entry.timestamp)` instead.

- ui/views.py `api_inventario_add` and `api_inventario_detail`: the HTTP status is picked by searching the Italian text of the `ValueError` raised in ui/services/inventory.py (`"già presente" in str(exc)`, `"non trovato" in msg`). On PUT every other message becomes 404 and on POST every message becomes 409, so "Valore booleano non valido" or "La manutenzione è disponibile solo per Testa e Generatore." answer 404/409 instead of 400, and rewording a message silently changes the status. Nothing in ui/services raises `RuntimeError`, so the four `except RuntimeError` → 503 branches and the "503 when the database is not yet available" docstring lines are dead. Raise typed exceptions (duplicate, not found, invalid) from inventory.py, map them to 409/404/400 in the view, and drop the 503 branches.

- ui/views_ottimizzazione.py `api_ottimizzazione_spiegazione` and `api_ottimizzazione_accetta`: the final `except Exception:` returns a generic 500 ("Errore durante l'applicazione della proposta.", "Errore durante la generazione della spiegazione.") without logging anything, so an unexpected failure while applying an accepted optimization leaves no trace. Add `logger.exception(...)` in both handlers.

- ui/views_import.py `api_inventario_import_excel`, ui/views_ottimizzazione.py `api_ottimizzazione_accetta` and ui/views.py `_handle_deadline_update`: these three write endpoints never call `record_operation`, although ui/services/operation_log.py states that every human-facing mutating endpoint calls it exactly once. A bulk inventory import, an accepted optimization and a deadline change do not appear in Impostazioni → Log. Add one `record_operation` call to each (imported/skipped counts, number of activities updated, commessa and new deadline).

- ui/services/problem_detection.py `overdue_not_started` and `sync_overdue_problems`, reconcile.py `ensure_daily_sync`, resource_availability.py `availability_map` and `annotate_inventory_rows`, optimization_problem.py `_due_date`, `build_scheduling_problem`, `build_reschedule_problem` and `schedule_metrics_from_tasks`, optimization_explanation.py `format_optimization_result_for_llm`, and ui/views.py `inventario`: "today" is `date.today()` (OS timezone) in these functions and `django.utils.timezone.localdate()` (Europe/Rome) in `bridge_write.py`, `planning_read.py`, `resource_conflicts.py` and `overlap_reassign.py`. On a host whose clock is not on Rome time the two differ by a day around midnight: the "NON INIZIATA · SCADUTA" badge and the `ritardo` note switch on different days, and `test_default_horizon_is_tomorrow` in ui/tests/test_optimization.py compares `problem.horizon_start` (built from `date.today()`) with `localdate() + 1`. Replace every `date.today()` in ui/services and ui/views.py with `localdate()`.

- ui/services/excel_importer.py module docstring and `parse_excel` docstring: they give the column order as categoria, uid, misura, note, stabilimento and mark all five as required, but the code reads column 4 as the plant and column 5 as the note (`plant = _str_or_none(cells[3])`, `note = _str_or_none(cells[4])`, which is also what the help text in ui/templates/ui/inventario.html shows) and only checks categoria and uid. Correct the two docstrings to the order and requirements the code applies.

- ui/views.py `pianificazione`: `stabilimenti`, `responsabili` and `tipi_attivita` are built as `sorted(set(orm_list + get_xxx()))`, but `get_stabilimenti`, `get_responsabili` and `get_tipi_attivita` in ui/services/activity_inventory.py read the same three models, so each list is merged with itself at the cost of three extra queries per page load; the docstring still says the dropdowns come from "ORM-managed and imported sources". Use each helper once (keeping the `nome`/`colore` query needed for `plant_colors`) and fix the docstring.

- ui/permissions.py `admin_required`: no view uses it (the only references are its own module docstring and README.md "Access layers", which says the `write_required` / `admin_required` decorators wrap every mutating view of the web app and the tablet bridge, while the bridge uses `bridge_write_guard` in ui/views_bridge.py). Remove the decorator and correct the README sentence and the module docstring to name the guards really in use.

- ui/models.py `Attivita.tp60_custom` comment and ui/services/activity_inventory.py (comment above `pre_testa = _select_n(...)`): both say a TP60 Custom activity has consumable minimums at 0 and starts with no mandrini, tastatori or maschere ticked, but `TP60_CUSTOM_REQUIREMENTS` in the same service is `{"mandrini": 2, "tastatori": 0, "maschere": 1}` and README.md documents "2 mandrini and 1 maschera, no tastatore". In the same family, the `ProblemaAttivita` docstring in ui/models.py says "Two kinds exist" while six `TIPO_*` are defined, and docs/dataset.md still lists the table `risoluzione_problema`, dropped by ui/migrations/0037_finalize_job_fk.py. Rewrite the two comments, the docstring and the docs line to match the code.

- ui/templates/ui/impostazioni.html, the three `data-modello="{{ ...|escapejs }}"` attributes in `#tbody-config-testa`: `escapejs` is only decoded in a JavaScript context, so in an HTML attribute a model such as "HT-200" is read back by `dataset.modello` as the literal `HT-200`. For any model containing `-`, `&`, `=`, `;` or quotes the "add configuration" dropdown offers models already configured, the edit modal title shows the escaped text, and re-adding a generator chip posts the escaped string as `modello_generatore`. Drop `|escapejs` from the three attributes (template autoescaping is enough there).

- ui/templates/ui/pianificazione.html `_wizAppendRow`: when the wizard creates a new commessa the group header is built with `_pianGroupHeadHtml({ commessa: r.commessa, n_activities: 0 })`, ignoring the `job` argument that carries the server's `job_id`, `delivery_date`, `total_cost` and `penalty`. Until the page is reloaded the card shows no deadline and its edit modal opens empty, so saving any change from it sends nulls and `api_jobs_update` in ui/views.py overwrites the three fields. Build the header from `job` when it is present.

- ui/templates/ui/inventario.html `submitImport`, `showImportBanner` and `showImportResult`: when `/api/inventario/import-excel/` imports part of a file it returns the rejected rows in `errors`, but the page only shows "✓ Importate N risorse…" and reloads after two seconds; the branch of `showImportResult` that lists `res.errors` is unreachable because the function is only ever called with `type: 'error'`. When `data.errors` is not empty, show the list and skip the automatic reload.

- ui/tests/fixtures/gantt_actual_window_test.mjs, gantt_badge_anchor_test.mjs, gantt_badge_anchor_rules_test.mjs, gantt_badge_completed_test.mjs, gantt_badge_inprogress_test.mjs, gantt_dependency_test.mjs, gantt_stable_width_test.mjs: they use literal 2026 dates with `chart.render(tasks, 'year')`, and the year view of ui/static/ui/gantt.js `render` is the current calendar year (`floorYear(today)`), so from 1 January 2027 no bar is drawn and the seven fixtures fail. Build the dates relative to today as gantt_overrun_test.mjs does. Also ui/tests/fixtures/gantt_start_offscreen_test.mjs is run by no Python test: register it next to the others in ui/tests/test_gantt_results.py.

- ui/services/bridge_write.py `update_attivita`: `item_value = str(data["item"]).strip()` turns a JSON `"item": null` into the literal item `"None"`, which passes the empty check and is saved; `a.tp60_custom = bool(data["tp60_custom"])` turns the string `"false"` into `True`. Refuse a null item with the existing 400 ("Il valore di item è obbligatorio.") and parse the flag with the same rule as `_parse_bool` in ui/services/inventory.py.
